# 0003 — the document layer is the tree-sitter grammar

- **Status:** accepted
- **Date:** 2026-09-13
- **Deciders:** the maintainer

## Context

satz-studio edits `.satz` files in place: a value is replaced, and every comment, every
blank line, the alignment of `=` and the order of entries stay as they were. That needs
a lossless view of the file: byte ranges for every node, comments as nodes, and the
original text recoverable by identity.

`satz_core::satz::parse` cannot provide it. Its lexer discards comments and whitespace,
its nodes carry a 1-based line and nothing finer, and `File` splits params, claims,
questions, actions and `hcl` blocks out of `items`, so source order is unrecoverable.
It is the authority on what a file means, and stays that; it is not a document layer.

The plan for the app proposed a hand-written lossless parser inside the app. Between the
plan and the scaffold, a tree-sitter grammar for Satz came into existence in its own
repository of its own, `satz-tree-sitter`: it mirrors satz's front-end token for token,
its gate is zero errors over every `.satz` file of a satz checkout, and satz's Zed
extension pins a commit of it (satz ADR 0016, `vendor/satz/docs/adr/`). A tree-sitter
tree is a lossless concrete syntax tree: every node has byte ranges, comments are
nodes, and the parser is generated from a grammar that is already kept in step with
satz's parser.

## Decision

The document layer is built on the tree-sitter grammar. The generated parser
(`src/parser.c`, `node-types.json`, `grammar.json`, `tree_sitter/`) is vendored under
`vendor/satz-tree-sitter/src`, with the commit it was taken from in
`vendor/satz-tree-sitter/COMMIT`; `crates/satz-studio-core/build.rs` compiles it with
`cc` into the core crate; `cst::grammar::language()` exposes it to the `tree-sitter`
crate. The `Cst` of `crates/satz-studio-core/src/cst/mod.rs` is built over that tree:
`Node` and `NodeKind` with byte `Span`s, `text()` the file itself, `scan_uses` reading
the commented `use` lines from comment nodes.

Meaning stays with satz-core. `Cst::lower` hands the same text to
`satz_core::satz::parse`, and every edit must be accepted by it before it is written.
A test in `cst/grammar.rs` parses every smoke estate with both and fails when either
refuses a file.

The vendored parser is refreshed by `scripts/sync-grammar.sh`, by hand, from a
checkout of the grammar repository. A construct the grammar mis-reads is fixed in the
grammar repository, never worked around in the app.

## Consequences

- One description of the language's surface serves the editor and the app. Where the
  grammar and `satz.rs` disagree, the grammar is the bug, and the corpus parse finds it.
- The app carries no parser of its own to keep in step. What it carries is a copy of
  generated C, refreshed by hand: a language change in satz reaches the app as a
  grammar commit, a sync, and a submodule bump.
- The `tree-sitter` crate and the generated parser must agree on the ABI
  (`tree-sitter = "0.27"` and a parser generated by tree-sitter-cli 0.27); a mismatch
  fails at `set_language`.
- The build needs a C compiler on every platform, which `cc` finds.
- The grammar's known limit carries over: an `hcl { … }` body is a brace-balanced rule,
  so a heredoc with unbalanced braces inside one mis-parses the rest of that block.
- The vendored copy is generated code, and it is what lets CI and a clone
  without access to it build the app.

## Pros and cons of the options

### A — a hand-written lossless parser inside the app

- **Good:** no C, no generated code, node shapes that are exactly the app's.
- **Bad:** a second hand-written description of the language beside `satz.rs`, and a
  third beside the grammar, drifting from both; every language change is three parsers
  to touch. It duplicates a mechanism that exists.

### B — re-lex the source for trivia and align to satz-core's AST by line number

- **Good:** the least code: a tokenizer plus a join on `line`.
- **Bad:** a heuristic exactly where an editor must be exact. Several entries on one
  line (`local { path = "…" }`), lists and objects spanning lines, `"""` strings
  shifting line counts, and `File` losing source order all break the join, and a wrong
  join writes a value into the wrong span.

### C — a git submodule of the grammar repository

- **Good:** one pin, the same way satz is pinned.
- **Bad:** the vendored parser is a copy, so a grammar change reaches the app only
  when `scripts/sync-grammar.sh` is run and `COMMIT` moves; nothing fails while the
  copy is behind the grammar.

### D — vendor the generated `src/`, compile it in `build.rs` *(chosen)*

- **Good:** the grammar that already mirrors satz's parser, with byte ranges and
  comment nodes, built into the crate from a public tree; `COMMIT` says which grammar.
- **Bad:** a manual refresh step and a copy of generated code in the tree; a C compile
  in the build.
